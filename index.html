Engineering philosophy

How I work

Start from the person using it.

A guest at a packed event, a caller on a phone line, a tribe owner checking orders. I design around their situation first and pick the technology after.

AI earns its place.

I add a model where it removes real work or makes something new possible. Everywhere else, plain code is cheaper, faster and easier to trust.

Own it end to end.

From the data model to the deploy pipeline to the support message on launch day. Owning the whole path is how a product stays coherent.

Boring where it counts.

Payments, authentication and money movement get proven patterns and careful testing. I save the experiments for places where a mistake is cheap.

Technical notes

Payments

Taking payments when the network gives up

Why Tokens by Kairams keeps the guest's phone out of the payment entirely.

At large events, thousands of phones compete for a few cell towers. Any payment that needs the guest's phone online fails at the worst moment, in a queue at a food stall.

So the guest carries a prepaid card with a printed QR code instead. They recharge it before the event. Only the stall staff need a connection, and they get one over the venue's own Wi-Fi.

The QR code only identifies the card. The 6-digit PIN authorises the debit, the same way an ATM card works. Anyone who photographs a card still can't spend from it.

Architecture

One platform, many storefronts

Structuring Tribe Merchandise so every tribe sees only its own business.

Each tribe needed its own customers, orders, stock and wallet, plus a public storefront. The admin needed to see everything at once.

The answer was one codebase with tenant-scoped data. Every request carries the caller's role and tribe, and the API scopes each query by them. Admin routes are a separate surface rather than a flag on the tribe routes.

Storefronts follow the same rule from the outside: a public URL per tribe that only ever reads that tribe's catalog.

AI

Counting calories from a photo

What I learned putting a vision model behind a Telegram chat in ScaleWise.

Logging food is where most diet apps lose people. A photo is the lowest-effort input there is, so ScaleWise starts there.

The model returns an estimate, not a fact. The bot shows what it thinks it saw and the calories it assigned, and the user can correct it in one message. The daily budget always reflects the corrected number.

Chat was the right interface. There's no app to install, and the same conversation handles logging, recipes, meal plans and workouts.

APIs

Designing APIs for a phone call

What changes when the client of your API is an IVR system.

A caller can't see a screen or retry a click. Every pause on the line feels long, so the APIs behind an IVR have to answer quickly and predictably.

Identity has to work from what a caller can key in. Customers are recognised by their registered mobile number and agents by their agent ID, and each gets different self-service options.

Responses stay small and unambiguous, because each one becomes a sentence the system speaks out loud.
